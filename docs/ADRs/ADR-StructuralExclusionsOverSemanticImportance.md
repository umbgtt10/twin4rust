# ADR-StructuralExclusionsOverSemanticImportance

- **Status:** Accepted
- **Date:** 2026-08-16

## Context

Not every source file deserves a mirrored test. A file holding one enum and its
imports has nothing to assert that the compiler has not already proved. Forcing
a test file for it produces a stub that exists only to keep a gate quiet, which
is worse than no file at all — it looks like coverage.

But "deserves a test" is a slope. Once the tool starts deciding which files
matter, it needs a notion of importance, and every project disagrees about
where that line sits.

## Decision

Exclusions are decided from the `syn` AST by structure alone. The tool never
infers semantic importance, and an ambiguous file stays visible rather than
being silently dropped.

## Forcing constraints / Evidence

Two structural categories cover the real noise:

1. **Definition-only files** — every top-level non-test item is a `struct`,
   `enum`, `type`, `trait`, `const` or `static` declaration, an ignorable item
   (`use`, `extern crate`, bodiless `mod`), or a trait impl carrying no
   methods. There is no executable behaviour to test.
2. **Single-type files whose only `impl` is a trivial `new`** — one method, no
   generics, returns `Self`, body is a single struct literal, no branching, no
   loops, no helper calls. A pure data holder.

Both are decidable by walking items. Neither requires knowing what the type
means, who calls it, or how important it is.

Analysis runs on a parsed `syn::File` with no type resolution and no build
step, so the tool works on any syntactically valid source whether or not the
crate compiles or its dependencies are vendored.

## Rejected alternatives

- **Line-count or item-count thresholds.** Arbitrary, and wrong in both
  directions: a 200-line const table needs no test, a 12-line parser does.
- **Path heuristics such as excluding `types/` or `model/`.** Encodes one
  project's directory taste as policy.
- **Resolving types to detect data-holder-ness properly.** Requires a compiling
  crate with vendored dependencies, which loses the ability to run on a broken
  tree — exactly when a structural gate is most useful.

## Consequences

Classification cannot see through a type alias or a macro expansion. A data
holder generated by a derive macro, or one whose `new` delegates to a helper
for readability, is reported. That is the intended direction of error:
ambiguity resolves toward visible rather than silent.

An empty file — no top-level items at all — is deliberately *not* treated as
definition-only, and is reported. An empty source file is more likely an
accident than a decision.

## Enforcement

`DefinitionAnalyzer` and `TrivialConstructorDetector` take `&str` and a parsed
`syn::File` respectively; neither has access to a resolver, a manifest or a
filesystem. `tests/definition_analyzer_tests.rs` and
`tests/trivial_constructor_detector_tests.rs` pin both categories, including
the negative cases — a `new` with branching, a trait impl with a method, a
second method on the type.
